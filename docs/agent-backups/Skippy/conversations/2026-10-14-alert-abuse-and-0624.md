# Alert-tree abuse drills + 0.6.24 logic holes (Skippy, 2026-10-14)
Read-only. one-to-many @ 69ada9b (0.6.24, includes the 0.6.23 override). Files: docs/ALERT-LOGIC-TREE.md, AlertLogicTree.kt, PushGate.kt. There is no 0.6.24 screenshot folder, so this review is code-only. Life-safety bias: no fix below may make a real zero-trust warning about a threat headed at someone fail silently. The worst a fix can do is downgrade a push to "SHOW + needs confirm" while still showing it.

## JOB A: attack drills (ranked)
1. **Made-up heading aimed at a victim.** Setup: a zero-trust report sets its own heading and speed toward phone X. pickTrack prefers the REPORT track over OFFICIAL and RADAR (AlertLogicTree.kt:165-167). The cone covers X, sev ≥ 4, so the zero-trust override pushes (:241-243, :253; PushGate.kt:31-32). Safe: if a radar or official track exists and disagrees by more than a heading Param, use it for the cone; the report track is used only when no other track exists. Fix: prefer OFFICIAL > RADAR > REPORT for the cone, and record a disagreement as "conflicting heading" on the map.
2. **No-track 2-mile push.** Setup: a zero-trust report with no heading, claimed severity 5, within 2 mi of X. noTrackNear takes the raw reportedSeverity (:230), and the in-path gate accepts noTrackNear (:241), so it pushes. A missing heading also passes the heading check because `headingOffDeg ?: 0.0` (:243) fails open. Safe: still SHOW on the map. Fix: for zero-trust plus no track, push only with a second independent report or a device signal (Param). Treat a missing heading as unknown, not 0°. **Flag for Chris:** does a lone zero-trust "tornado here, no heading" within 2 mi push? Life-safety argues yes, harassment argues no.
3. **Harassment of one phone.** Setup: an attacker repeats #1 or #2 against one person's last known area. Nothing in the tree or PushGate rate-limits pushes per reporter or per target (PushGate.kt:31-46). Safe: the first push goes through. Fix: per-reporter push budget (Param), per-target dedupe window, an auto "refuted" mark when officials or radar never confirm, and the user can tap "this is false" (it counts toward reporterBlockFloor, :54).
4. **"It passed" / away-heading suppression.** Setup: a report with a heading AWAY from X. Because REPORT wins the track pick (:166), a radar-only threat is computed as "behind/not closing", so sev 0 (:232-233). The official floor (:236) protects only official-covered users. Safe: never let a report track *lower* a radar or official track. Fix: the lowest-risk track can't win; take the max severity across available tracks.
5. **Claimed-low severity.** `minOf(reportedSeverity, coneSeverity)` (:229) lets any reporter lower a real in-cone severity. Safe: a report claim may lower its *own* contribution, but must never lower a fused or radar-based severity. Fix: per-source severity, then max across sources (unknown how AlertHub fuses multiple reports; verify).
6. **Wrong side of the storm.** Setup: a report from behind the storm with a heading that puts X ahead. along/closing are computed from the given storm point (:173-185), with no check that the reporter stood where they claim. Fix: proof of presence. The report point must be within a Param of the device's recent GPS track, and a mismatch flags it "location doesn't match movement". **Unknown**: no such check found in the tree or PushGate.
7. **Replay of an old real report.** TreeInput has no timestamp or nonce (ALERT-LOGIC-TREE.md:64), and the tree has no age check. Fix: signed envelope with HLC and a replay window (PR #1). Report age greater than a Param means sev decays and no push. **Unknown**: the envelope path in AlertHub isn't verified.
8. **Spam flood and sybil accounts.** newReporterOptIn is ON by default (:52), and blocking needs refuted marks first (:105-107). Zero-trust sybils each get the override. Fix: device attestation weight, burst collapse (many new keys in minutes count as 1), and the same per-reporter budget as #3.
9. **Edge-of-cone tricks.** zeroTrustConeMarginMi defaults to 0 and "edge counts as inside" (:48, doc line 13). Unknown margin also defaults to 0.0 (:240). A heading tuned to graze the edge pushes. Fix: if the margin is unknown, treat it as "unknown → needs 2nd source" rather than 0. Keep edge = inside for corroborated reports (life safety).
10. **Alert storm / fatigue.** There's no global push cooldown or collapse of repeated alerts for one threat (PushGate.kt:41-46). Fix: one push per threat ID, then quiet updates in place. The user's dial-back still never silences critical alerts (Q4 off, :245-246).
11. **Trust farming.** record = confirmed − refuted (:105). An attacker builds a good record cheaply, then cashes it in with a trusted life-threat solo push in grid-down (:258). Fix: trust decays with time; confirmations must come from independent sources; a sudden behavior change (first ever sev 5, far from the usual area) gets a Param trust discount.
12. **Severity scale is fixed.** SEV_MAX = 5 is an identity, which is fine (:161-162). But trustWeight index 0 = 0.0 hard-codes "zero trust" (:35). It's tunable, but if a user sets it above 0, zeroTrust (:239) never triggers and the zero-trust safeguards disappear silently. Fix: key zero-trust on "no record", not on weight ≈ 0.

## JOB B: 0.6.24 logic holes
1. Report-track priority (AlertLogicTree.kt:165-167) lets crowd data override official and radar geometry. This is the root cause of drills 1 and 4.
2. A missing heading or margin fails open (:240, :243).
3. noTrackNear uses the raw claimed severity (:230), the only path where a reporter's claim *raises* severity, which contradicts doc line 23 "claim never raises".
4. PushGate has no rate or dedupe (PushGate.kt:41-46). `flush()` clears pending even when a push failed the gate (:46), so a crowd push deferred while officials were up is dropped rather than re-evaluated if officials then go down. Make re-evaluation explicit.
5. The PushGate header still says "hard gate, NOT a setting… crowd-only can NEVER push" (PushGate.kt:4-11), but the 0.6.23 override (:31-32) does push crowd-only. The doc and comment are stale.
6. `silenced` uses `sev < lifeThreatSev + raise` (:246). With LOW (+1), a sev-4 life threat can be silenced when the user opts in, but sev 5 never can. If Chris meant "all critical", this is inconsistent. **Flag for Chris.**
7. 0.6.24 committed a compiled `tools/__pycache__/testonly_seal.cpython-313.pyc` (69ada9b stat). Repo hygiene: add it to .gitignore.
8. PhotoShare: `trustLevelVerified` is always false (PhotoShare.kt:80), so the unblurred path is dead code behind a Settings toggle (:88). The UI should say "not available yet", not offer a toggle that can't take effect.
